## 1. პროექტის აღწერა

ქალაქში დაზიანებული განათების, გზის ორმოს ან გადავსებული ურნის შესახებ მოქალაქეს არ აქვს მარტივი გზა, რომ მუნიციპალიტეტს შეატყობინოს და შემდეგ გაიგოს, მოგვარდა თუ არა პრობლემა. **FixIt** არის მობილური აპლიკაცია, რომლითაც მოქალაქე იღებს ფოტოს, ირჩევს კატეგორიას, უთითებს ადგილს GPS-ით ან რუკაზე და აგზავნის განაცხადს. მუნიციპალიტეტის დისპეჩერი ვებ-პანელიდან ამოწმებს განაცხადს და ანიჭებს საველე თანამშრომელს, რომელიც მობილური აპლიკაციით იწყებს სამუშაოს და დასრულებას ფოტოთი ადასტურებს. მოქალაქე ყოველ ეტაპზე ხედავს სტატუსს, მუნიციპალიტეტი კი იღებს ერთიან აღრიცხვასა და პასუხისმგებლობის ისტორიას.

## 3. Product Goal და MVP

**Product Goal:** 2027 წლის 31 იანვრისთვის მოქალაქეს შეუძლია ტელეფონით ერთ წუთში გააგზავნოს პრობლემა ფოტოთი და მდებარეობით, დისპეჩერი მას თანამშრომელს ანიჭებს, თანამშრომელი სამუშაოს ფოტოდადასტურებით ამთავრებს, მოქალაქე კი ყოველ ეტაპზე ხედავს სტატუსს.

**MVP (ყველა Must have, 10 story, 39 SP)** მოიცავს სრულ ციკლს ერთ მუნიციპალიტეტში:

1. მოქალაქე რეგისტრირდება და შედის მობილურ აპლიკაციაში (US-18, US-01).
2. ქმნის განაცხადს კატეგორიით, აღწერით, 1-3 ფოტოთი და მდებარეობით (US-02, US-03).
3. ხედავს მხოლოდ საკუთარ განაცხადებს, დეტალებსა და სტატუსის ისტორიას (US-04).
4. ადმინისტრატორი ქმნის თანამშრომლების ანგარიშებს და ანიჭებს როლებს (US-13).
5. დისპეჩერი ვებ-პანელიდან ხედავს უწყების განაცხადებს და ანიჭებს თანამშრომელს (US-08, US-09).
6. თანამშრომელი იწყებს სამუშაოს და ამთავრებს მას ფოტოთი; მოქალაქე ხედავს სტატუსს `Resolved` (US-11, US-12).

| პრიორიტეტი | Story-ები | რაოდენობა | ქულა |
|---|---|---:|---:|
| Must have | US-01, US-02, US-03, US-04, US-08, US-09, US-11, US-12, US-13, US-18 | 10 | **39** |
| Should have | US-05, US-06, US-10, US-14, US-19 | 5 | 16 |
| Could have | US-07, US-15, US-16, US-20 | 4 | 16 |
| Won't have (ამ ეტაპზე) | US-17 | 1 | 3 |
| **სულ** | | **20** | **74** |

**MVP-ში არ შედის:** push-შეტყობინებები, ელფოსტით შეტყობინებები, საჯარო რუკა, უარყოფა და დუბლიკატები, კატეგორიების მართვა, პაროლის აღდგენა, მხარდაჭერის ხმები, სტატისტიკა, შეფასება, ხელახლა გახსნა და ანონიმური შეტყობინება. ეს ფუნქციები Product Backlog-ში რჩება და იგეგმება, თუ სიჩქარე დაგეგმილზე მაღალი აღმოჩნდება.

**დიდი Story-ების დაშლა:** ორიგინალი EPIC-ები შეფასდა 13 და 8 ქულით, რაც ერთ სპრინტში ვერ ეტევა. ისინი დაიშალა დამოუკიდებლად შესამოწმებელ Story-ებად (BACKLOG-ში ველი "დაშლილია"). Backlog-ში არცერთი Story არ აღემატება 8 ქულას.

**სიჩქარის კონტროლი:** Sprint 1-ის შემდეგ რეალური სიჩქარე შედარდება დაგეგმილს. თუ ის 6 SP-ზე ნაკლებია, MVP-ის თარიღის შესანარჩუნებლად US-03-ში საზღვრის შემოწმება მარტივდება (მართკუთხა საზღვარი PostGIS პოლიგონის ნაცვლად) და Product Owner გადახედავს ფარგლებს. თუ სიჩქარე 10 SP-ზე მეტია, Sprint 4-5-ში ემატება Should have Story-ები (US-19, US-10, US-14).

### 5.4 Definition of Ready

Story შეიძლება აირჩეს Sprint Planning-ზე, როცა:

- აქვს ფორმატი "როგორც ..., მსურს ..., რათა ..." და Given/When/Then Acceptance Criteria;
- შეფასებულია Fibonacci ქულით (≤ 8) და მინიჭებული აქვს MoSCoW;
- ყველა დამოკიდებულება დასრულებულია ან იმავე სპრინტშია;
- ცნობილია საჭირო API endpoint და მონაცემთა ცვლილება (ARCHITECTURE-ის მიხედვით).

### 5.5 Definition of Done

Story გადადის `Done`-ში მხოლოდ მაშინ, როცა:

- [ ] ყველა Acceptance Criteria შემოწმებულია;
- [ ] ახალ ბიზნესლოგიკას აქვს Unit/Integration ტესტი; API-ს ცვლილებას აქვს WebApplicationFactory ტესტი; ბიზნესლოგიკის დაფარვა ≥ 70%;
- [ ] Backend ამოწმებს როლს და რესურსის მფლობელობას; 401/403 შემთხვევები ტესტირებულია;
- [ ] build, lint, type check და CI წარმატებულია; არ არის ცნობილი Critical/High ხარვეზი (Dependabot);
- [ ] Pull Request გადახედულია (self-review ჩეკლისტით);
- [ ] ფუნქცია გაშლილია staging-ზე და შემოწმებულია;
- [ ] მობილური: შემოწმებულია Android-ზე და iOS სიმულატორზე, 360 dp სიგანეზე; კამერის/GPS-ის უარყოფისას აპი არ იშლება; ტოკენები ინახება SecureStore-ში;
- [ ] ვები: შემოწმებულია ≥ 1024 px-ზე; ფორმებს აქვს სერვერული ვალიდაცია; Cookie/CSRF პოლიტიკა შემოწმებულია;
- [ ] ფაილები: ზომა და რეალური ფორმატი მოწმდება, EXIF იშლება, ფაილი private საცავშია, შეცდომისას ფაილი არ რჩება უპატრონოდ;
- [ ] API, მონაცემთა მოდელი და migration განახლებულია ARCHITECTURE-ში; GitHub Issue აღწერს შედეგს.

**Privacy Check** (იურიდიული სამსახურის ვეტოს გამო) ტარდება ორჯერ: Sprint 2-ის ბოლოს (ფოტო და მდებარეობა) და Sprint 5-ის ბოლოს, MVP-ის გაშვებამდე.

```text
README.md                 პროექტი და პროცესი

ARCHITECTURE.md           არქიტექტურა, API, ბაზა, deployment
backlog/stories.json      Story-ების ერთადერთი წყარო

scripts/                  Backlog-ის გენერაცია, შემოწმება, GitHub sync, პრეზენტაცია
```

```bash
python scripts/validate_backlog.py        # ქულები, Fibonacci, AC, დამოკიდებულებები და სპრინტები
python scripts/build_backlog.py           # stories.json-დან BACKLOG.md

```

Story იცვლება მხოლოდ `backlog/stories.json`-ში, შემდეგ გაეშვება validate, build და sync. სკრიპტებს სჭირდება Python 3.10+; sync-ს დამატებით GitHub CLI (`gh auth login`).
